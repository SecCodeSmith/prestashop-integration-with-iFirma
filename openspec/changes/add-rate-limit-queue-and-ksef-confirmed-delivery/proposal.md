# Proposal

## Why

iFirma allows 100 API requests per minute and 15,000 per day per account (shared with every other client of the account), but the module only counts its own requests per minute and has no answer for the server's own refusal. When many orders reach the trigger status in a short time, the automatic issuance of the later ones is refused by the local guard and is silently dropped: nothing is recorded and nothing retries, or the refusal is stored as an `error`. The status hook writes the order's record only as a side effect of a finished pipeline step. A refused guard check, or a shop request that ends before a step finishes, therefore leaves no record and no log line. A missing document cannot even be traced: on the two local test shops, 13 and 5 orders reached the trigger status with no record, and nothing tells whether they were skipped on purpose or dropped. Separately, since April 2026 iFirma can submit API-issued invoices to KSeF on its own (at a time set in its settings) and refuses to e-mail invoices that belong in KSeF. The module does not detect that, so it can submit the same invoice a second time. It also hands the invoice to the customer before KSeF has accepted it, which is too early: an invoice given outside KSeF should carry its KSeF number.

## What Changes

- **Daily rate cap next to the minute cap.** The module counts its requests per calendar day as well as per minute and refuses to start a request above either cap. The minute cap stays at default 80; a new setting `IFIRMA_RATE_MAX_PER_DAY` defaults to 14,000 and allows at most 15,000. No hourly window: iFirma documents none.
- **Server limit answers start a back-off.** An HTTP 429, or an answer whose message says the request limit was exceeded, counts as "rate limited", not as an error or an unknown outcome. The module then sends nothing until the time the server asked for (`Retry-After`, otherwise the next minute).
- **Queue-first issuance.** When an order reaches the trigger status, the status hook records it as `queued` before any iFirma request. It then tries to issue the order at once under the per-order lock, which the hook path takes for the first time, without waiting for it.
  - A rate-limit refusal (local caps or iFirma), a busy lock, or a request that ends before the create leaves the order `queued` instead of dropping it.
  - Just before the create request is sent, the record becomes `unknown` (in flight). A request that dies mid-create therefore never leads to a blind second create.
  - Employee Create, bulk retry and the Orders-list bulk issue also queue an order the rate limit refused.
  - The cron endpoint issues queued orders oldest first, through the same pipeline and duplicate guard, up to a per-run cap (`IFIRMA_CRON_MAX_ITEMS`, default 10), and stops at the first refusal.
  - A queued record older than 30 minutes is listed as needing attention, so a shop without a cron job notices.
- **No double KSeF submission.** A new setting `IFIRMA_KSEF_SUBMITTER` (`module` by default, or `ifirma`) says who submits. With `ifirma` the module never calls the KSeF send endpoint; it only waits for the KSeF state that iFirma reports. With `module`, the module first reads the document's current KSeF state from iFirma and does not submit when iFirma has already sent or scheduled it. If that state cannot be read, nothing is submitted and the cron tries again. Manual **Send to KSeF** applies the same check.
- **Delivery after KSeF acceptance.** A document that goes to KSeF under the configured mode (B2B invoices in `b2b`, every supported invoice in `all`) is not e-mailed at issuance. Its delivery state becomes `awaiting_ksef`, and the cron delivers it once status sync reports it accepted (KSeF number or `PRZYJETA`). Until then the customer's order page shows no download link and the download answers "not found". Receipts, invoices to private buyers in `b2b` mode, and every document in mode `off` are delivered at issuance as today. A manual **Send again** still delivers at once and ends the wait. A rejected submission, or a wait longer than 48 hours, needs attention.
- **Orders list: readable status on hover, and sorting by status.**
  - The iFirma icon's tooltip says in words what happened, in the employee's language. Its first line names the kind and the state, for example "Faktura wystawiona", "Faktura wysłana", "Faktura opłacona", "Faktura czeka na KSeF" or "Paragon wystawiony". Lines for delivery, payment and KSeF follow.
  - An order without a document shows its state ("Błąd wystawienia: …", "W kolejce (limit iFirma)", "Brak dokumentu" …) with the hint to click to issue.
  - The column becomes sortable, ascending with the orders that need action first: failed, unknown, suspected, held, queued, no document, then issued, waiting for KSeF, sent, paid.
- **Cron runs four jobs in a fixed order.** Issue queued orders, retry deferred KSeF submissions, sync statuses (documents awaiting KSeF are always due), and deliver accepted documents. All four share the rate guard, take a run lock against overlapping runs, and report their counts in the JSON summary.
- **iFirma mock: limits and KSeF auto-send (test-stack).** The mock enforces a per-minute and a per-day limit, by default iFirma's 100 and 15,000 in the compose stack. A refused call gets HTTP 429 with `Retry-After` and a "limit exceeded" body. A test route changes the limits at runtime, and another simulates the next minute or day. New counters report rejected calls, today's calls and the busiest minute. A `ksef-auto` switch makes the mock behave like an iFirma account that submits new invoices to KSeF itself. Document detail answers carry `KsefStatus` and `KsefNumer`, and each document counts the KSeF send calls it received. The status page and the state file carry the new data. The mock version becomes 1.4.0.
- **End-to-end checks.** New smoke scenario R issues at least 50 documents in a row under the limits. It checks that every order ends with exactly one document, that the module never trips the mock's minute limit by itself, and that refusals from iFirma (minute and day) are queued and drained without errors or duplicates. New smoke scenario S checks KSeF-confirmed delivery: module submission, iFirma auto-send, submitter `ifirma`, rejection, and documents that do not go to KSeF. Existing scenarios D, F and N are updated for the new behaviour.
- **BREAKING (behaviour, no API change):** In KSeF mode `b2b` or `all`, invoices that go to KSeF are delivered only after acceptance. Every order that reaches the trigger status gets a `queued` record before any iFirma request, and automatic issuance refused by the rate guard stays queued instead of failing or leaving no trace. The cron endpoint does more than status sync; its JSON summary gains keys, and its existing keys keep their meaning.

## Capabilities

### New Capabilities

- `receipt-issuance-queue`: recording every order that reaches the trigger status as queued before any iFirma request, queuing issuance refused by the rate limit on every path, draining the queue from the cron endpoint within a per-run cap and under a run lock, and how a queued order shows in the back office.
- `mock-rate-limit`: the iFirma mock's simulated per-minute and per-day request limits, its 429 answer, the runtime limit and next-window routes, and the counters it reports.
- `mock-ksef-simulation`: the iFirma mock's KSeF behaviour beyond the send endpoint: the account-level auto-send switch, KSeF fields on the document detail, and per-document counting of KSeF send calls.
- `issuance-throughput-e2e-verification`: the end-to-end smoke scenario that issues at least 50 documents in a row under the minute and day limits, with local and server-side refusals.
- `ksef-delivery-e2e-verification`: the end-to-end smoke scenario for no double submission and delivery after KSeF acceptance.

### Modified Capabilities

- `ifirma-api-compliance`: the local rate guard counts per minute and per day; a server limit answer starts a back-off.
- `receipt-auto-issuance`: the trigger records the order as queued first and runs the pipeline under the order's lock; the record is marked `unknown` before the create request is sent.
- `receipt-duplicate-guard`: a guard check refused by the rate limit during automatic issuance queues the order instead of recording an error.
- `receipt-status-sync`: the cron endpoint runs the queue, KSeF retry, sync and delivery jobs; documents awaiting KSeF are always due for sync; the summary gains counts.
- `ksef-submission`: the submitter setting, the KSeF state read before any submission, cron retry of deferred submissions, and the readable states for documents sent by iFirma or rejected.
- `receipt-delivery`: documents that go to KSeF are delivered after acceptance instead of at issuance.
- `customer-receipt-visibility`: a queued order shows the not-issued state; a document awaiting KSeF acceptance shows no download link and cannot be downloaded.
- `receipt-documents-list`: the needs-attention preset gains queued and KSeF wait conditions; a refused issuance in a bulk run is queued, and the hint names the window that refused.
- `order-list-receipt-indicator`: the icon's tooltip names the document kind and state in words, with delivery, payment and KSeF lines; the Issue action's tooltip names the not-issued state and the short error; the column sorts by state; the order refused during a bulk issue is queued.
- `receipt-issue-notifications`: issue events gain KSeF rejection, an overdue KSeF wait and a stale queue.
- `mock-status-page`: limits, new counters, the `ksef-auto` switch and per-document KSeF send counts are shown and can be changed from the page.
- `mock-state-persistence`: the day window, the runtime limits, the `ksef-auto` switch and the per-document KSeF send counts survive a restart.

## Impact

- **Module code:** `IfirmaApiClient` (the rate guard moves to its own class with minute and day windows, server-limit detection and back-off), `IfirmaIssuancePipeline` (queue-first status hook under the order lock, queued outcome, delivery hold), `IfirmaReceiptService` (a rate-limited create is no longer an `error`; the in-flight `unknown` marker before the create request), `IfirmaKsefService` (submitter, state read before submission, KSeF-bound check), `IfirmaDeliveryService`, `IfirmaStatusSyncService` (selection), new cron jobs and a runner behind `controllers/front/cron.php`, `IfirmaBulkRunner`, `IfirmaIssueFeed`, `IfirmaCustomerView`, `IfirmaAdminPanelPresenter`, `IfirmaOrderGridIndicator` (more selected fields and the state rank), a new `IfirmaOrderGridTooltip`, the Orders-grid hooks in `ifirma.php` (sortable column, ORDER BY in the query-builder hook), the receipt download controller, `IfirmaSettings`, `IfirmaSchema` (config defaults), `upgrade/upgrade-1.7.0.php`, the module version 1.7.0, admin and customer templates, and translations.
- **Database:** no new column. New values `queued` (record state) and `awaiting_ksef` (delivery state) fit the existing VARCHAR columns. New configuration keys: `IFIRMA_RATE_MAX_PER_DAY`, `IFIRMA_RATE_DAY_WINDOW`, `IFIRMA_RATE_BACKOFF_UNTIL`, `IFIRMA_KSEF_SUBMITTER`, `IFIRMA_CRON_MAX_ITEMS`.
- **Tests:** new and updated unit tests in `tests/Unit` (rate windows, back-off, queue, cron runner, KSeF check, delivery hold, customer download, Orders-list tooltip and sort), settings golden fixture, the Orders-grid smoke check `tests/smoke/order-grid-check.php`, smoke scenarios R and S plus updates to D, F and N.
- **test-stack (submodule, separate repository):** `app/store.py`, `app/main.py`, `app/config.py`, `app/ui.py`, `app/state.py`, the pytest suite, `docker-compose.yml` (limits on by default, mock timezone), the README, and version 1.4.0. The module pins the new submodule commit.
- **Docs:** `docs/configuration.md` (rate limits, cron, KSeF submitter), `docs/usage.md` (queue, KSeF delivery), `docs/architecture.md`, `docs/troubleshooting.md`, `docs/upgrading.md`, `tests/smoke/README.md`.
- **Operations:** shops should call the cron endpoint every 1 to 5 minutes. Queued orders and documents awaiting KSeF are processed there. Without a cron job, they wait for the bulk **Retry issuance** or a manual **Send again**.
- **Release:** a minor version (1.7.0) with a new cron job, settings and an upgrade script. It counts as a major update under CLAUDE.md, so a red-team pass runs before release.
