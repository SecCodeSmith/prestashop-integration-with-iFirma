# Proposal

## Why

A merchant who runs the module on a busy shop cannot work failed documents in bulk: a failed issuance, an unknown outcome, a suspected duplicate or a failed e-mail delivery is visible only inside the one order it belongs to, so the merchant finds out late and repairs one order at a time. At the same time the module has no role model: its admin tab is hidden (`id_parent = -1`), so only the SuperAdmin profile holds its permissions and no other profile can be granted anything from the Permissions page, while the panel still renders for every employee and every state-changing AJAX action (issue, issue anyway, send to KSeF, register payment, approve or reject a data request) is protected by the admin token alone on PrestaShop 8 (the legacy controller flow runs `ajaxProcess*` after the token check only) and by the tab's "view" access on PrestaShop 9. A read-only security audit of the module (2026-11-07, findings S1 to S17 recorded in design.md) found no critical issue but a cluster of medium ones that belong in the same hardening pass: unvalidated payment amount and API base URL, no protocol restriction on the cURL transport, no back-off after an authentication failure, an unthrottled customer PDF proxy, and internal exception text returned to the browser.

## What Changes

- **iFirma documents list (new back-office page).** A list page under *Orders > iFirma documents* (the module tab, now visible in the menu) shows the module's records with filters on state, delivery state, KSeF state, order reference, number and dates. Row actions open the order, retry the issuance, resend the e-mail, refresh from iFirma and download the PDF. Bulk actions on the selected rows: **Retry issuance** (records in `error`, `unknown`, `duplicate_suspected` or `held` without a pending request, each run through the identical issuance pipeline, so the duplicate guard still runs and nothing is retried blindly), **Resend e-mail** (issued documents, including delivery `failed`) and **Refresh from iFirma**. A bulk run works in batches under the module's per-minute rate guard, stops at the cap instead of failing the remaining rows, and ends with a per-row summary (issued, adopted, sent, refused, rate limited).
- **Issue from the Orders list.** On the back-office Orders list the empty "iFirma" cell of an order without an issued document becomes an **Issue** action for employees allowed to issue, and the list gets the bulk action **Issue iFirma documents** for the selected orders, with the same batching and summary as above. The column keeps its icon and tooltip for issued documents.
- **"iFirma" tab in the back-office notifications.** The header notification centre (the bell with the Orders, Customers and Messages tabs) gets a fourth tab, **iFirma**, listing the newest document issues: failed issuance, unknown outcome, suspected duplicate, held order, failed delivery, failed KSeF submission and a document that disappeared from iFirma. The bell counter includes the issues the employee has not seen yet; opening the tab marks them seen for that employee only. Each entry links to the order, and the tab footer links to the documents list filtered on issues. The tab is built from local records only, polls at the same cadence as the core notifications, and is shown only to employees allowed to see documents. On a back-office layout where the core notification centre cannot be found, the module falls back to a standalone bell button next to it rather than failing.
- **Roles.** Three levels, managed where PrestaShop manages every other permission, *Team > Permissions*, on the module's tab: **View** (see the order panel, the Orders-list column, the documents list, the notification tab, the customer-page contractor panel, download PDFs), **Add** (issue: create, issue anyway, link a duplicate candidate, register a contractor, bulk issue and retry) and **Edit** (manage issued documents: resend, register payment, send to KSeF, refresh, approve or reject a data request, bulk resend and refresh). Every back-office entry point of the module enforces its level server-side and answers a refused call with a permission message; the panels hide what the employee may not do. The settings page stays under the module's *Configure* permission. SuperAdmin keeps everything; other profiles keep what they have today, which is nothing, until granted. **Behaviour change:** employees of a profile without View no longer see the order panel, the column or the customer-page panel, which until now rendered for everyone while their actions failed.
- **Security hardening** (the audit findings that are fixed in this change; the rest are listed in design.md with the reason they are deferred):
  - S1 permission gate on every state-changing admin action (covered by the roles above);
  - S3 the paid amount sent to iFirma is validated (numeric, positive, two decimals, not above the order total) and refused otherwise;
  - S4 the API base URL must be an absolute `https` URL (plain `http` only for a dev-mode shop), and the transport allows only HTTP(S), never follows redirects and caps the response size;
  - S5 an authentication failure from iFirma (HTTP 401/403, or `Kod` 400 to 403 and 499, the account-wide credential and terms errors) stops further calls for a cool-down period, is never retried with waits, is shown as a banner on the settings page and is cleared when credentials are saved;
  - S2 the customer PDF download is throttled per document so a looping customer cannot exhaust the shared rate cap;
  - S6, S7, S16 admin and front error responses carry a generic message as plain text with `nosniff`, the detail goes to the log, the PDF file name is sanitised on both download paths and every PDF response carries `nosniff`;
  - S9 API keys are password inputs that keep the stored value when posted empty, and the cron endpoint also accepts its token in a request header so it can stay out of access logs;
  - S10 download and cron tokens come from the CSPRNG only, with no weaker fallback;
  - S11 the per-minute rate counter is incremented atomically;
  - S12, S13 data-change requests validate names, address, postcode and country with the shop's validators, cap the note lengths, and a customer may submit at most one request per order per cool-down window;
  - S14, S15, S17 array values posted for scalar settings or tokens are refused instead of raising a type error, the optional keys are hex-checked on save, and the delivery e-mail escapes the customer variables.
- **Upgrade.** A new upgrade script moves the module tab into the Orders menu, registers the new hooks and keeps every existing permission row. The change ships as a `minor` release so the script runs on upgraded shops.
- **Docs and translations.** usage.md (documents list, bulk actions, Orders-list actions, notification tab, roles), configuration.md (permissions, key fields, cron header), architecture.md (new classes, security notes), upgrading.md, README changelog; Polish translations for every new string.

## Capabilities

### New Capabilities

- `receipt-documents-list`: the back-office list of the module's document records: what it shows, how it filters, the single and bulk operations it offers (retry issuance, resend, refresh), how a bulk run behaves under the rate guard and what it reports.
- `receipt-issue-notifications`: the "iFirma" tab of the back-office notification centre: which events count as an issue, the unseen counter, the per-employee seen mark, the links, the polling and the fallback when the core centre is absent.
- `receipt-access-control`: the three permission levels of the module (view, issue, manage), which actions and screens each one gates, how they are granted, their defaults on install and upgrade, and the refusal behaviour.
- `module-endpoint-security`: the input validation, error disclosure, response header and secret-handling rules of the module's HTTP endpoints and settings page (back office and front office).

### Modified Capabilities

- `order-list-receipt-indicator`: "Empty cell without an issued document" becomes an Issue action for employees allowed to issue (empty for the others), and the list gains the bulk action "Issue iFirma documents".
- `ifirma-api-compliance`: "Local rate guard" counts atomically; new requirements for the authentication-failure cool-down, the base URL validation and the transport restrictions (protocols, redirects, response size).
- `customer-receipt-visibility`: new requirements for the per-document download throttle and for the download token coming from a CSPRNG only.
- `receipt-status-sync`: "Cron endpoint authentication" also accepts the token in a request header; the cron token comes from a CSPRNG only.
- `invoice-data-change-request`: "Request content and validation" gains the field validators and length caps; a new submission cool-down requirement.
- `customer-contractor-panel`: "Access control on panel actions" additionally requires the module's View level for the panel and its read actions.

## Impact

- **Code.** `ifirma.php` (tab under Orders, new hooks for the header script and the Orders-list script, permission-aware hook rendering, password key fields, auth-failure banner), `controllers/admin/AdminIfirmaController.php` (permission gate, bulk endpoints, notification feed, hardened error responses), a new list controller for the documents page, new classes for the permission check, the bulk runner, the issue feed and the seen mark, `classes/IfirmaApiClient.php` and `IfirmaHttpTransport.php` (auth cool-down, atomic counter, protocol and size limits), `IfirmaSettings.php` (URL rule, array-safe text, hex rules), `IfirmaReceiptService.php` (amount validation, CSPRNG only), `IfirmaDataRequestService.php` (validators, cool-down), `IfirmaHttpOutput.php` (headers), `controllers/front/receipt.php` and `cron.php`, the order panel and customer panel templates, a new back-office script and stylesheet, `upgrade/upgrade-1.5.0.php`, `translations/pl.php` and `tools/pl_translations_map.php`.
- **Database.** No new table. One new nullable column on the receipt table for the download throttle (`last_download_at`) and an index on `date_upd` for the notification feed, both added by the upgrade script (the column is also self-healed at runtime like the KSeF columns); the per-employee seen mark and the auth cool-down are configuration values; the tab row is updated in place.
- **PrestaShop surface.** The module tab moves from hidden to *Orders > iFirma documents*; one new hook (`actionAdminControllerSetMedia`, which fires on legacy and Symfony back-office pages on both versions) carries the two back-office scripts; the Permissions page lists the module tab. PrestaShop 8.0 to 9.x stay supported; the notification tab degrades to a standalone button where the core centre is not found.
- **iFirma API.** No new endpoints. Bulk operations reuse the existing create, list, detail, PDF and send calls and stay under the existing per-minute guard; the auth cool-down reduces calls after a credential failure.
- **Tests.** New unit tests for the permission check, the bulk runner, the issue feed, the amount and URL validation, the transport options, the cool-down, the throttle and the token generation; extended controller tests for the permission gate and the bulk and feed endpoints; a smoke script on the Docker shops for the documents list, the Orders-list bulk action and the notification tab; the visual check on PrestaShop 8.1 and 9.1.
- **Deferred (not in this change).** S8 (synchronous retry waits inside the order-status hook) and encryption of the API keys at rest; both are recorded in design.md with their reason.
