# Proposal

## Why

Customers who checked out as guests cannot ask for a billing-data correction today, because the data-change form (`/module/ifirma/datarequest`) requires a logged-in owner of the order; they end up e-mailing the shop, and the merchant copies the data by hand. Every request, even a harmless postcode fix, also waits for an employee, which holds the automatic issuance of the document in the meantime. Finally the module's e-mails and the iFirma document itself carry no shop branding, unlike PrestaShop's own e-mails.

## What Changes

- **Guest request page with a one-time code.** A new front page lets a visitor who is not logged in identify an order by its reference and the order e-mail. The module e-mails a single-use numeric code (the password-reset pattern: short lifetime, limited attempts, generic answers that do not reveal whether the order exists). After the code is verified the visitor gets the same data-change form, the same validation and the same limits as the logged-in form, and can also cancel their pending request. Logged-in customers keep the existing form unchanged.
- **Auto-accept criteria for data-change requests.** A new setting (`none` / `safe` / `all`, default `none` so upgrades keep today's behaviour) lets the module approve a valid request without an employee. In mode `safe` a request is approved automatically only when it keeps the buyer identity: same company/private choice, same NIP (or still none) and same company name; only the name, address lines, postcode, city and country may change. Auto-approved requests are recorded as approved by the system, visible as such in the admin order panel, the customer receives the approval e-mail, the merchant notification says the request was approved automatically, and the issuance resumes immediately as it does after an admin approval.
- **Shop logo in the module's e-mails.** Every e-mail template the module ships (receipt issued, data request received / approved / rejected, and the new one-time code mail) shows the shop logo in its header through PrestaShop's `{shop_logo}` placeholder, which the core mailer embeds as an inline image.
- **Shop logo on the receipt through the iFirma print template.** The iFirma PDF is rendered by iFirma, so the module does not stamp it; instead a new setting names the iFirma print template (`NazwaSzablonu`, for example the account's logo template) that is sent with every document the module creates. Empty (the default) keeps iFirma's default template. The documentation explains that the logo itself is uploaded in the iFirma account.
- **Configurable order stamp prefix.** Several shops can share one iFirma account; today every shop stamps `PS-ORDER-{id_order}-{reference}` into `Uwagi` and `DodatkoweUwagi`, so the duplicate guard and adoption can confuse documents of different shops. A new per-shop setting replaces the first segment (for example `scmedical-15-ABCDEFGHI`, `hialumed-15-ABCDEFGHI`); the default `PS-ORDER` keeps today's stamps, and documents issued before a prefix change are still recognised by their legacy stamp.
- **Shop webpage.** A new setting holds the shop's public address (empty means the shop's own URL). The logo and shop name in every module e-mail link to it and the footer prints it; when configured it is printed in the document comments after the order stamp; and every PDF file name (customer download, admin download, e-mail attachment) becomes `{shop-domain}-{document-number}.pdf` instead of `ifirma-{number}.pdf`, so documents of several shops can be told apart in a mailbox or a download folder.
- Mock, smoke scenarios, unit tests, translations and docs updated accordingly; module version bump with an upgrade script for the new table, column and settings.

## Capabilities

### New Capabilities

- `guest-order-verification`: proving, without a customer login, that the visitor controls the e-mail of an order: identification by reference and e-mail, issuance and delivery of a single-use code, lifetime and attempt limits, anti-enumeration answers, and the short verified session the code opens.
- `module-mail-branding`: the shop logo and shop name in the header of every e-mail the module sends, both linking to the shop webpage, the footer address, the shop-webpage setting itself, and the plain-text fallback.

### Modified Capabilities

- `invoice-data-change-request`: eligibility extended to a verified guest requester (the order's own customer record, not a login); new auto-accept requirement with the `safe` criteria and the system resolution; audit trail and admin panel show an automatic approval; merchant notification names an automatic approval; the guest form reuses content validation, CSRF, cool-down and cancellation.
- `ifirma-api-compliance`: a new "Document print template" requirement: the configured template name is sent as `NazwaSzablonu` on `fakturakraj`/`fakturaparagon` create requests, omitted when empty, validated on save.
- `receipt-duplicate-guard`: the order reference stamp gets a configurable first segment (default `PS-ORDER`), `Uwagi` carries the shop webpage after the stamp when configured, and the confirmed-match adoption also accepts the legacy `PS-ORDER` stamp after a prefix change; new "Stamp prefix setting" requirement.
- `module-endpoint-security`: the PDF file name becomes `{shop-domain}-{name}.pdf` on both download paths and the e-mail attachment.

## Impact

- **Code:** `controllers/front/` (new guest controller), `classes/IfirmaDataRequestService.php` (auto-accept path), new classes for the auto-accept criteria and the one-time code store, `classes/IfirmaSchema.php` (new table and column), `classes/IfirmaSettings.php` + `ifirma.php` (two settings, form, defaults, uninstall), `classes/IfirmaPayloadBuilder.php` (`NazwaSzablonu`, stamp prefix, webpage in `Uwagi`), `classes/IfirmaDuplicateMatcher.php` + `IfirmaDuplicateGuard.php` (legacy stamp match), `classes/IfirmaHttpOutput.php` + `IfirmaDeliveryService.php` (file names), `classes/IfirmaCustomerView.php` and `views/templates/hook/order_detail.tpl` (link for guests on the guest-tracking page), `views/templates/front/` (new template), `mails/{en,pl}/` (logo in 4 templates, 1 new template), `translations/pl.php`, `upgrade/upgrade-1.6.0.php`, admin order panel presenter (automatic approval label).
- **Test stack:** `test-stack/ifirma-mock` stores and shows `NazwaSzablonu` (version bump); smoke scenarios for the guest code flow (code read from the SMTP sink), auto-accept and the template field; unit tests and golden fixtures.
- **Docs:** `docs/usage.md` (guest flow, auto-accept), `docs/configuration.md` (two settings, where the logo is configured in iFirma), `docs/troubleshooting.md` (code not received, template unknown to iFirma).
- **Compatibility:** no breaking change. New settings default to today's behaviour (`none`, empty template, `PS-ORDER` prefix, empty webpage). The one visible default change is the PDF file name, which now starts with the shop domain instead of `ifirma-`; anything that matches the old name pattern (mail filters, scripts) needs to be told. The iFirma behaviour for a template name that does not exist in the account is not documented and could not be verified against the live API; the mock accepts any name and the troubleshooting note covers the error path.
- **Security:** a new unauthenticated endpoint. It answers identically whether or not the order exists, rate-limits code issuance per order and per client address, stores only a salted hash of the code, limits verification attempts, and never exposes order data before the code is verified.
