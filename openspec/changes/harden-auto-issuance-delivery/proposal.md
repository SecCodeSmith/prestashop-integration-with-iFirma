# Proposal

## Why

On 2026-11-04 the merchant reported an automatic issuance (order status trigger, payment method `TPA`) whose order panel showed the contractor step as *tryb awaryjny* with the note "iFirma created the contractor but neither identifier (PS-C1909 / PS-C1909) can be read back" and, after issuance, "iFirma przypisała kontrahenta IFI1909556979"; the delivery step of the same run failed because the PDF of the just-issued document could not be downloaded from iFirma, so the customer received nothing until a manual **Send again**. The module gives up on both steps after a single try: the contractor is read back only by identifier, immediately after the create call, and the PDF is requested exactly once, immediately after the document is created. The merchant also asked for a copy of every delivery e-mail, either to the shop mailbox or to a chosen back-office employee, which the module cannot do today.

## What Changes

- **Contractor read-back after creation.** When iFirma confirms the create call (`Kod` 0), the module reads the contractor back by the sent identifier and by the identifier iFirma reported, accepting both the documented list shape and a single-object `Wynik`; when neither answers, it waits briefly and reads back once more; when that still fails it searches for the contractor it just created (exact NIP for a business buyer, otherwise the buyer name confirmed by e-mail or postcode) and uses the identifier iFirma actually stored (for example `IFI1909556979`), linking the customer to it. Fallback mode (document without a reference) is reached only when every read-back fails.
- **Fallback diagnostics.** The fallback note stored on the receipt names each identifier tried and the answer iFirma gave for it (`Kod` and `Informacja`, or "empty result"), and the `created` note names the identifier iFirma assigned when it differs from the one sent. The notes written by the contractor step are translatable, so the Polish back office no longer shows an English sentence inside a Polish label.
- **PDF download retry in shop-mail delivery.** When the PDF fetch fails for a reason that can clear with time (transport error, HTTP 5xx, 404 or 429, a non-PDF answer, or an iFirma "document not found" code), the delivery step waits and tries again, at most three attempts with waits of 3 s and 7 s (10 s in total, the merchant's suggested bound). Authentication and configuration errors and refusals by the local rate guard are not retried. The recorded failure names the number of attempts and the last error. The customer-page download keeps its single attempt.
- **Copy of the delivery e-mail.** Two new settings, `IFIRMA_SEND_COPY_MODE` (`none`, `shop`, `employee`; default `none`) and `IFIRMA_SEND_COPY_EMPLOYEE` (employee id, default 0), add a blind-copy recipient to the shop-mail e-mail that carries the PDF: the shop contact address (`PS_SHOP_EMAIL`) or the e-mail of an active employee chosen from a list on the configuration page. The copy applies to automatic delivery, to the shop-mail fallback of the iFirma-mail channel, and to **Send again**; it never applies to e-mails sent by iFirma itself. An unresolvable copy address (employee removed, inactive or without a valid e-mail, or equal to the customer address) is skipped and logged, and the customer e-mail is still sent. The configuration page refuses to save an `employee` mode without an existing active employee.
- **Test stack.** The mock gains two test-only switches: a contractor-create mode that stores the contractor under its own generated identifier while echoing the sent one in `Wynik` (the live behaviour observed), and a counter that makes the next N PDF downloads answer "document not found". New smoke checks cover both paths end to end.
- **Documentation.** README "Delivery" describes the retry and the copy settings, "Linking existing contractors" describes the read-back sequence, "Configuration keys" lists the two new keys, and "Troubleshooting" gains an entry for *tryb awaryjny* explaining the note and what to check.
- Assumptions recorded for the merchant: the copy is sent as a blind copy (BCC) because PrestaShop's mail layer offers no visible CC; `TPA` in the report is the payment-method line of the order panel (Tpay), not a separate defect; the real cause of the failed read-back is not determinable from the code, so the change covers the three plausible causes (identifier replaced by iFirma, read-after-write delay, unexpected answer shape) and records the answer for the next incident.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `ifirma-api-compliance`: gains "Created contractor read-back" (the read-back sequence after a confirmed create: identifier, delayed retry, search; fallback only when every step fails; the identifier iFirma stored is the one referenced and mapped) and "Contractor step notes" (what the fallback and created notes carry and that they are translated). "Contractor registration before issuance" keeps its text: its "Contractor API unavailable" scenario still describes the final fallback.
- `receipt-delivery`: gains "PDF download retry in shop-mail delivery" (bounded retry on transient failures, attempt count in the recorded error), "Copy of the shop-mail delivery" (blind-copy recipient, resolution and skip rules) and "Delivery copy settings" (configuration fields and validation). "Shop-mail channel" keeps its text: "PDF cannot be fetched" still holds once the attempts are exhausted.

## Impact

- **Code:** `classes/IfirmaContractorService.php` (create read-back sequence, `Wynik` shapes, delayed retry, search after create, note texts with translation, injectable wait), `classes/IfirmaReceiptService.php` (hands the module to the contractor service so its notes translate; created note with assigned identifier), `classes/IfirmaDeliveryService.php` (PDF retry with injectable wait, retryable-error classification, blind-copy recipient resolution and `bcc` argument), `ifirma.php` (two form fields with the employee list, validation, save, read-back, `created` label with message), `classes/IfirmaSchema.php` (configuration defaults), `translations/pl.php` and `tools/pl_translations_map.php` (new strings), README.
- **Tests:** `tests/Unit/ContractorServiceTest.php`, `tests/Unit/ContractorReferenceTest.php`, `tests/Unit/DeliveryServiceTest.php`, `tests/Unit/IssuancePipelineTest.php` (delivery tests must inject a no-wait sleeper), `tests/Unit/ModuleHooksTest.php`, `tests/Unit/ConfigurationKeysTest.php`, `tests/Unit/SchemaTest.php`, `tests/Unit/TranslationCoverageTest.php` (new strings must be translated); stubs `tests/Stubs/Employee.php` (employee list and loading), `tests/Stubs/PrestaShopLogger.php` (copy skipped log). Test stack (separate repository `test-stack/`): `ifirma-mock/app/main.py`, `ifirma-mock/app/store.py`, pytest cases, and `tests/smoke/run.php` plus `tests/smoke/README.md` in this repository.
- **Behaviour visible to merchants:** fewer documents issued in fallback mode and, when it still happens, a note that says what iFirma answered; an e-mail that previously failed right after issuance now goes out within about ten seconds; the order status change request can take up to ten seconds longer only when the PDF is not ready; a copy of each delivery e-mail reaches the shop or the chosen employee once the merchant enables it (default off, so nothing changes on update).
- **iFirma API usage:** at most two extra `kontrahenci` calls per newly created contractor (one delayed read-back, one search) and at most two extra PDF requests per delivery, only on the failure paths. The daily limit is unaffected on the normal path.
- **Data:** no schema change; two new configuration keys with defaults written on install and upgrade and removed on uninstall. The `_contractor` note in `request_payload` gains optional keys (`assigned_identifier`, `readback`) that older panels ignore.
